# Google Drive Telegram Bot — 凭证管理执行策略（中文版）

本文将原始的凭证管理优化方向细化为可执行的实施步骤与验收标准，目标是为 Telegram 机器人构建一套多租户、安全且易维护的 Google OAuth 凭证管理机制。

## 1. 用户级凭证存储

在执行以下策略前，需要通过环境变量或 `.env` 文件为机器人提供运行所需的 Telegram 与 Google OAuth 配置。仓库附带 `.env.example` 供部署时复制为 `.env` 并填写真实值，避免在源码中存放任何密钥。

### 1.1 文件布局与权限
- **实施步骤**
  1. 在机器人启动脚本（`bot/__main__.py`）中创建可配置的凭证根目录，默认使用 `user_data/`。
  2. 按照 `user_data/token_<user_id>.json` 的命名规则为每个 Telegram 用户保存 OAuth 凭证。
  3. 创建或更新凭证后立即设置目录权限为 `0o700`、文件权限为 `0o600`，保证仅机器人进程可访问。
  4. 在启动阶段添加权限自检逻辑，如权限异常则给出告警并可选地自动修复。
- **验收标准**
  - 新环境首次部署后，会在服务启动前自动创建 `user_data/` 并赋予正确权限。
  - 上传等操作仅能从 `token_<user_id>.json` 读取凭证，未发生跨用户读取。
  - CI/QA 检查脚本可在 Linux 环境验证权限位是否符合预期。

### 1.2 首次授权与凭证再生成
- **实施步骤**
  1. 在上传命令处理器中引入 `ensure_user_credentials(user_id)` 辅助函数，所有 Drive API 调用前都先执行它。
  2. 辅助函数检测凭证文件是否存在；如不存在则发起 Google OAuth 授权流程，并以“写入临时文件再原子重命名”的方式保存凭证。
  3. 如果读取到的凭证 JSON 格式错误或被篡改，自动删除文件并重新触发授权流程。
- **验收标准**
  - 用户首次执行上传操作时会被引导完成授权，授权完成后上传顺利执行。
  - 被破坏或不完整的凭证文件能够在不影响服务稳定的情况下自我修复并重新授权。

## 2. 凭证生命周期模块

### 2.1 凭证校验模块（`bot/helpers/credentials/validator.py`）
- **实施步骤**
  1. 新增 `load_and_validate(user_id)` 方法，返回已授权的 Google API 客户端或抛出类型化异常。
  2. 使用 Google 官方库解析凭证 JSON，检查过期时间及刷新令牌信息。
  3. 为每条校验路径输出结构化日志（info/warn/error），便于追踪。
- **验收标准**
  - 单元测试覆盖：凭证有效、凭证过期、缺失 refresh token、凭证文件损坏等场景。
  - 日志中包含用户 ID、事件类型、关联 ID，并对敏感字段进行脱敏。

### 2.2 凭证存储模块（`bot/helpers/credentials/storage.py`）
- **实施步骤**
  1. 实现 `write_credentials(user_id, credentials_dict)`，使用 UTF-8 编码序列化 JSON，并通过 `tempfile.NamedTemporaryFile` 保证原子写入。
  2. 使用 `fcntl.flock` 等机制实现建议性文件锁，避免多个工作进程竞争写入导致数据损坏。
  3. 提供 `read_credentials(user_id)`，将“文件不存在”和“JSON 无效”区分为不同异常，便于上层处理。
- **验收标准**
  - 通过多进程模拟的竞争测试，验证不会出现部分写入或文件损坏。
  - 存储模块返回的错误信息清晰且不会泄露 token 内容。

### 2.3 凭证加载模块（`bot/helpers/credentials/loader.py`）
- **实施步骤**
  1. 将 Google Drive 客户端创建集中在 `get_drive_client(user_id)`，内部依赖存储、校验和刷新模块。
  2. 为每个用户按需懒加载 Drive Service 对象，可在单个请求/会话内缓存以提升性能。
  3. 统一抛出 `MissingCredentials`、`InvalidCredentials`、`RefreshRequired` 等标准化异常，方便上层处理逻辑。
- **验收标准**
  - 上传、克隆、删除等操作全部通过该加载模块获取客户端。
  - 集成测试验证在凭证更新后，缓存客户端能正确反映最新凭证状态。

### 2.4 凭证刷新模块（`bot/helpers/credentials/refresh.py`）
- **实施步骤**
  1. 封装 Google 官方刷新流程，实现 `refresh_credentials(user_id, credentials)` 并返回更新后的凭证。
  2. 处理 HTTP 异常、刷新令牌被撤销等失败场景，并回退到重新授权流程。
  3. 与校验/加载模块集成：当 `expiry <= now` 时自动刷新并持久化最新凭证。
  4. 将刷新结果写入安全审计日志。
- **验收标准**
  - 凭证到期后可在用户操作中自动刷新，无需用户手动干预。
  - 如果 refresh token 被撤销，会向用户输出重新授权提示并终止当前操作。
  - 审计日志记录刷新成功或失败的时间戳与用户 ID。

## 3. 安全与隐私增强

### 3.1 凭证隔离控制
- **实施步骤**
  1. 将 Telegram 用户 ID 与凭证文件路径进行严格映射，杜绝任意路径遍历。
  2. 在每次读写前校验路径与用户 ID 是否匹配，不符合则拒绝并输出警告日志。
  3. 添加跨用户访问的回归测试用例。
- **验收标准**
  - 自动化测试确认用户 A 无法读取或覆盖用户 B 的凭证。
  - 安全日志会记录被拒绝的访问尝试（匿名化处理）。

### 3.2 可选的凭证加密
- **实施步骤**
  1. 新增配置项 `ENABLE_CREDENTIAL_ENCRYPTION`，默认 `False` 以保持兼容。
  2. 当启用时，使用环境变量提供的密钥，采用 AES-256-GCM 对凭证内容进行加密。
  3. 在 JSON 文件中同时保存随机 nonce 与密文，文件名保持不变。
  4. 存储与加载模块根据配置透明地加解密。
- **验收标准**
  - 切换配置无需修改代码，适配环境变量或配置文件方案。
  - 解密失败会提示用户重新授权，不会暴露明文。
  - 安全评审确认使用了带认证的加密模式，并在可行范围内清理内存中的密钥。

### 3.3 日志脱敏
- **实施步骤**
  1. 设计统一的日志工具函数，接收上下文信息并自动对 `access_token`、`refresh_token` 等敏感字段脱敏。
  2. 在所有凭证相关模块中使用该工具，替换原有的 logger 调用。
  3. 配置日志输出（stdout 及可选文件）的滚动与保留策略。
- **验收标准**
  - 手工抽查与自动扫描均无法在日志中找到 token 明文。
  - 授权、刷新、拒绝访问等安全事件可追踪到时间和用户。

### 3.4 备份策略
- **实施步骤**
  1. 编写备份脚本，默认排除 `user_data/token_*.json`；若启用加密，可选择备份密文。
  2. 将备份操作纳入部署/运维手册，明确执行频率和恢复流程。
  3. 若启用加密，要求备份介质（如 S3）再次使用静态加密（例如 SSE）。
- **验收标准**
  - 备份流程不会收集明文凭证。
  - 灾难恢复演练能在不破坏用户隔离的前提下恢复机器人配置。

## 4. 错误与异常处理手册

| 异常场景 | 预期系统行为 | 验收标准 |
| --- | --- | --- |
| 凭证文件不存在 | 给出授权链接并终止当前操作。 | 手工测试：删除凭证后触发上传，收到提示并在重新授权后恢复。 |
| 凭证损坏 | 删除旧文件、记录警告日志并提示重新授权。 | 单元测试验证损坏文件会触发清理与提示。 |
| `user_data/` 缺失 | 自动重新创建目录并设置安全权限。 | 启动测试确认目录会自动创建。 |
| 尝试访问他人凭证 | 拒绝操作、记录安全日志，可选地通知管理员。 | 安全测试模拟伪造用户 ID 并验证被拦截。 |
| 授权失败或网络中断 | 向用户展示友好的重试提示，并保留状态方便再次尝试。 | 手工测试通过模拟网络超时验证提示效果。 |

## 5. 系统交互与流程更新

1. `/start` 或 `/upload` 处理器首先调用 `ensure_user_credentials`。
2. 若需要授权，机器人向用户发送 OAuth URL，并等待回调/轮询完成授权。
3. 授权成功后调用 `write_credentials` 持久化凭证，并反馈确认消息。
4. 后续上传操作通过加载模块复用缓存的 Drive 客户端。
5. 所有凭证相关事件都会记录到可配置的审计频道或日志文件。
- **验收标准**
  - 端到端测试脚本覆盖“注册 → 上传 → 凭证过期 → 自动刷新”的完整流程，无需人工介入数据库。

## 6. 质量保障

- **单元测试**：覆盖凭证校验、存储、加载、刷新、日志脱敏等模块。
- **集成测试**：模拟多用户并发上传、强制 token 过期等场景，验证隔离与自动刷新能力。
- **静态检查**：确保仓库中不存在硬编码的敏感信息或明文凭证。
- **文档更新**：向运维与支持团队提供授权流程说明及常见问题解答。

## 7. 维护与扩展

- 将凭证辅助模块封装为可复用组件，便于未来以 REST/gRPC 等形式对外提供服务。
- 为已部署的旧版本提供迁移脚本，将旧有凭证迁移至新目录结构和权限策略。
- 制定季度安全审查计划，重点检查加密密钥、Google 授权范围与审计日志完整性。
